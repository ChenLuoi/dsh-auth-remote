# Test guide

[简体中文](README.zh-CN.md)

This guide describes the eleven exact verification targets for plugin `0.2.0`. RC additions do not extend npm `0.1.10` historical support; final same-archive results are recorded separately.

Run tests from a Linux source checkout with Node.js 24+, pnpm 12.5.1, and Playwright Chromium:

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
pnpm check
```

`pnpm check` runs static checks and all four test groups. Run a group directly while developing:

| Group       | Command                 | Contract covered                                                                                                                                                  |
| ----------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit        | `pnpm test:unit`        | Password/TOTP/backup codes, sessions, origin policy, translations, JSON durability and lock recovery.                                                             |
| Integration | `pnpm test:integration` | Real HTTP and WebSocket sockets, Host/Origin policy, native readiness, cookies, API mutations and revocation.                                                     |
| CLI         | `pnpm test:cli`         | Real local archive, DSH profile execution, pseudo-terminal prompts, en/zh selection, JSON output, Unix socket, offline lock and uncertain results.                |
| Browser     | `pnpm test:browser`     | Pinned DSH boot, anonymous gate, login, Security & sign-in settings, native settings, workspace, chat stream, upload/preview, SSE/WebSocket and HTTPS forwarding. |

The scripts prepare DSH `0.2.1-rc.2` under `.cache/test-runtime/<version>` and create temporary `DSH_HOME` directories. `DSH_TEST_BIN` can override the executable only when `--version` reports the selected `DSH_TEST_VERSION` (default `0.2.1-rc.2`); `DSH_TEST_BROWSER` can override the Playwright browser executable. The default is Playwright-managed Chromium.

CI retains CLI/smoke for all eleven releases and selects browser coverage through the ordinary/full plan below. The exact targets are `0.1.7-rc.1`, `0.1.7-rc.2`, `0.2.0-rc.1`, `0.2.0-rc.2`, `0.2.1-alpha.1`, `0.2.1-alpha.2`, `0.2.1-alpha.3`, `0.2.1-alpha.4`, `0.2.1-alpha.5`, `0.2.1-rc.1`, and `0.2.1-rc.2`. Select a target with `DSH_TEST_VERSION=<version>`. Startup tests exercise the actual Loader and observe its model-facing Web section (runtime context on DSH `0.2.1-alpha.3`, `0.2.1-alpha.4`, `0.2.1-alpha.5`, `0.2.1-rc.1` and `0.2.1-rc.2`) and `DSH_WEB_URL`; native transport tests run IPv4/IPv6 HTTP/HTTPS and confirmed CLI revocation on DSH `0.2.1-alpha.2`, `0.2.1-alpha.3`, `0.2.1-alpha.4`, `0.2.1-alpha.5`, `0.2.1-rc.1`, `0.2.1-rc.2`, and assert unsupported IPv6/TLS errors on DSH `0.1.7-rc.1`, `0.1.7-rc.2`, `0.2.0-rc.1`, `0.2.0-rc.2`, `0.2.1-alpha.1`. Missing IPv6 or TLS test support fails the suite.

The Node HTTP/HTTPS forwarder in `tests/helpers/` stands in for transport without depending on a local proxy installation. `tests/fixtures/tls/` contains a dedicated self-signed test certificate and key for the `.test` hostname. They are never installation or production credentials and are excluded from the archive. Browser chat uses a local model stub. No real external account, OAuth token or paid model request is needed.

The [TLS fixture guide](fixtures/tls/README.md) documents the native listener certificate's IPv4/IPv6 SANs, Node trust and browser public-key pin. The forwarder also validates TLS upstreams, so both HTTPS-to-HTTP and HTTP-to-native-HTTPS chains have coverage.

Do not point these commands at an existing account directory. Browser and CLI fixtures use separate temporary homes; `pnpm smoke` uses the marked `.dev/dsh-home`. The [development guide](../docs/development.md) describes the isolated development lifecycle, and the [deployment guide](../docs/deployment.md) describes a live profile and backup procedure.

Login and official-account browser fixtures unset inherited `DEEPSEEK_API_KEY` in their DSH runtime environment so an inherited DeepSeek API key does not hide fresh-profile onboarding. The API-key setup helper selects the native credential alternative in the DSH `0.2.1-alpha.3`, `0.2.1-alpha.4`, `0.2.1-alpha.5`, `0.2.1-rc.1` and `0.2.1-rc.2` account dialog. Plugin-settings persistence checks also handle onboarding after an explicit page reload.

Official-account coverage in `integration/account-login.test.ts` uses the actual installed DSH `0.2.1-rc.2` provider from locked development dependencies and a local Platform stand-in to validate PKCE, redirect URI equality, state, callback parsing, session ownership, one-time submission, cancellation, expiry and retries. `browser/account-login.spec.ts` exercises instruction-first authorization, failed loopback navigation and pasted callback completion, blocked popups and bilingual responsive themes; DSH `0.1.7-rc.1`, `0.1.7-rc.2`, `0.2.0-rc.1`, `0.2.0-rc.2`, `0.2.1-alpha.1`, `0.2.1-alpha.2` verify startup, intact Settings and disabled manual account support. No real official account is used.

`browser/live-config.spec.ts` observes the real Loader and loaded package identities per release, writes true→false→true→false and verifies long connections and restart persistence. Full account-browser branches cover `0.2.1-alpha.3`, `0.2.1-alpha.4`, `0.2.1-alpha.5`, `0.2.1-rc.1` and `0.2.1-rc.2`, including native Settings save success/failure, immediate new-entry switching and completion of admitted attempts. Login/settings regression covers the five trusted overview values, password/TOTP/current/all-session dialogs, keyboard/focus, cancellation/errors, failed backup-code copying and one-time display. Screenshots mask passwords and backup codes. Full version matrices must reuse one final archive and check SHA-256 after each release, avoiding standard commands that repack inside the loop.

`browser/account-login.spec.ts` triggers real configuration HMR through an ordinary `sessionHours` change on all declared releases and verifies that Settings writes still wait for the native transaction queue and reject genuine nesting. The test-only `fixtures/hmr-config-probe.mjs` uses the real HMR service. The exact `0.2.1-alpha.3`, `0.2.1-alpha.4`, `0.2.1-alpha.5`, `0.2.1-rc.1` and `0.2.1-rc.2` targets also replace the isolated installed plugin entry and re-enable manual sign-in afterward.

The HMR queue case checks the precise startup maintenance message before and after configuration reload. A separate legacy case copies the same candidate's package manifest and dist into an isolated profile directory, disables the original host row, inserts the copied entry through the public Loader contract and opts into native source watching with explicit HMR `base/root`. It observes real module replacement and the next listener generation, then checks that the same process emitted the warning once and the session still works. Default legacy module watching excludes node_modules; this fixture does not claim automatic replacement there. Normal targets must not emit a maintenance warning. `unit/dsh-support.test.ts` verifies dates, unchanged classification after the deadlines, fictional retirement inputs and process-wide deduplication; these fixtures do not change a real host's version.

`browser/startup-compatibility.spec.ts` checks both rejection paths on `0.2.1-rc.1` and `0.2.1-rc.2`. Each isolated profile independently disables native webserver. Test-only changes to the installed plugin set an incompatible `engines.dsh` or replace its own admission range; upstream packages and exact versions are unchanged. The first must produce an actual skipped-bundle diagnostic without importing the plugin; the second must import it and reach its own runtime error. Startup must settle unsuccessfully without fixture termination, every TCP/HTTP/readiness/upgrade probe must get connection refused, and the profile patch must remain unchanged. These damaged copies provide refusal evidence only.

`browser/host-release.spec.ts` fixes four real round trips: `0.2.1-alpha.4` ↔ `0.2.1-alpha.3`, `0.2.1-alpha.5` ↔ `0.2.1-alpha.4`, `0.2.1-rc.1` ↔ `0.2.1-alpha.5`, and `0.2.1-rc.2` ↔ `0.2.1-rc.1`. Each keeps the page in one temporary profile/port, checks the native release prompt, reloads to verify authentication, the original session and persisted settings, then restores the starting release. Only `0.2.1-alpha.3` lacks release metadata and reads unknown; every other destination must show its actual full version. No upstream source, version or dependency-graph metadata is changed.

`browser/web-search-settings.spec.ts` registers only on `0.2.1-rc.2`. It opens the native Search/Fetch settings on an authenticated remote Host, verifies `web`, `web-search-deepseek` and `web-deepseek-api`, switches providers, saves endpoints/limits and a test credential, observes validation and an injected transport refusal, then verifies refresh and real process-restart persistence. Anonymous requests and the original cookie after session revocation must fail for settings and credential reads/writes. A local provider counts requests and must receive none; this verifies the settings/authentication boundary without Search/Fetch results, paid requests, or real account authorization. No host provider is replaced.

Fixed-archive verification uses `pnpm verify:packed --archive <archive> --sha256 <recorded-sha256> --dsh-version <exact-version> --suite <suite>` without rebuilding or repacking. The [development guide](../docs/development.md#consume-a-fixed-archive) lists all fixed suites and filter rules. The consumer restores the archive dist before CLI/installation checks, rejects empty or skipped runs, records SHA-256 and counts, and isolates smoke from `.dev` and port 13090. `unit/verify-packed.test.ts` covers damaged/escaping/link archives, actual Node zero-selection output and marked-root protection. Full release validation still requires every declared target's CLI, complete browser and smoke against the same archive.

CI uses the [ordinary/full plan](../docs/development.md#ordinary-and-full-ci-plans) with all-release CLI/smoke, three complete browser targets and fixed capability suites for the ordinary path; all source/infrastructure/unknown changes, manual/weekly runs and releases use complete eleven-release verification. Only the six exact documented paths permit reduction. Every required specialized file must register real tests, and unexpected skips fail. The first same-archive eleven-release full run precedes enabling reduction.
