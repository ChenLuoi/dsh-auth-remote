# DSH support history

[简体中文](support-history.zh-CN.md)

Pre-`0.2.0` registry baseline, checked on **2026-10-19** against the complete [DSH registry](https://registry.npmjs.org/@deepseek-ai/dsh) and [plugin registry](https://registry.npmjs.org/dsh-auth-remote): 36 DSH versions, 10 npm plugin versions, and the additional Git-only tag `v0.1.4`. All 36 DSH and 10 plugin archives were downloaded and their registry integrity values checked. Availability is a dated observation, not a compatibility or maintenance guarantee.

Start with [DSH → plugin](#by-dsh) or [plugin → DSH](#by-plugin). For current commitments, use the [support policy](support-policy.md) and [compatibility inventory](legacy-compatibility.md).

## Reading the evidence

- **D**: the exact version appears in the referenced manifest's `dsh.compatibility.dshReleases`. Each row separately identifies a published npm package, Git-only tag or unreleased source candidate; a declaration alone establishes neither availability nor a successful test.
- **R**: a release README reports that exact DSH version as tested or covered by its CI; its tagged CI/runtime identifies the same targets. This records the historical project's report, without claiming a surviving successful Actions run or a new run of that old archive.
- **R\***: a later README reports testing an earlier authentication implementation. It does not establish which old npm archive was exercised.
- **V**: a real run of an identified candidate archive in this development effort. The first eleven-version Node.js 24 run passed CLI, complete browser and installation smoke on one SHA-256. It applies to that unreleased candidate; the final archive must be verified again after all changes.
- **Unknown**: no exact pair was found in the checked npm manifests/READMEs, Git tags, CI/runtime files or changelogs. A peer/runtime range alone means technical admission, not D, R or V. An omitted pair is not proof of incompatibility.

The initial V record applies to an earlier candidate with working version `0.1.10`, not to `0.2.0`. It identifies SHA-256 `aac4843d079634e47b1d6e5a6f3c3bc4f7a29d41ec35c81993ab03bef6bb798e`, Node.js `24.21.0`, CLI 99/99, full browser 599/599 and smoke 11/11 on 2026-10-19. Raw reports are retained in maintainer verification records outside the npm archive. This history and later documentation postdate that archive; this record does not certify a revised final package.

Historical plugin rows are archived evidence, not continuously maintained per-version test matrices. DSH maintenance state is separate: plugin `0.2.0` keeps all eleven declared versions, including six legacy versions; none has actually retired. Legacy dates never automatically remove support. See the policy for exact dates and retirement requirements.

## Choosing an installation

For the eleven current DSH releases, select plugin **`0.2.0`** after its [exact registry endpoint](https://registry.npmjs.org/dsh-auth-remote/0.2.0) confirms availability. The release workflow verifies its final archive before publication. Follow the [deployment guide](deployment.md), including independent disabling of the native listener for protected remote use. The pre-release npm baseline was `0.1.10`, with nine declarations ending at `0.2.1-alpha.5`; historical availability does not make an old release preferred or newly verified.

DSH `0.2.1-rc.1` and `0.2.1-rc.2` require plugin `0.2.0`. During release preparation, use an explicitly verified source archive until publication succeeds. Version `0.2.0` does not change the bytes or promises of npm `0.1.10`, which must not be republished. No npm installation recommendation exists here for Git-only `0.1.4` or a DSH version with unknown history. Do not disable technical identity/API checks to force an old pair.

## Maintaining this history

These tables are maintained manually in both languages and both directions. Recheck registry metadata and tarball availability, inspect exact tag/package evidence, distinguish D/R/R\*/V, and record the check date. Update both cells when adding evidence; keep the stable anchors. A newly released plugin needs its own row and exact archive evidence. Actual DSH retirement updates current declarations, runtime adaptations, tests and this history together under the support policy; eligibility dates alone never change these tables. No inventory/history generator or dedicated CI gate is used.
