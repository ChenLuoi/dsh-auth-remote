## Reading the evidence

- **D**: the exact version appears in the referenced manifest's `dsh.compatibility.dshReleases`. Each row separately identifies a published npm package, Git-only tag or unreleased source candidate; a declaration alone establishes neither availability nor a successful test.
- **R**: a release README reports that exact DSH version as tested or covered by its CI; its tagged CI/runtime identifies the same targets. This records the historical project's report, without claiming a surviving successful Actions run or a new run of that old archive.
- **R\***: a later README reports testing an earlier authentication implementation. It does not establish which old npm archive was exercised.
- **V**: a real run of an identified candidate archive in this development effort. The first eleven-version Node.js 24 run passed CLI, complete browser and installation smoke on one SHA-256. It applies to that unreleased candidate; the final archive must be verified again after all changes.
- **Unknown**: no exact pair was found in the checked npm manifests/READMEs, Git tags, CI/runtime files or changelogs. A peer/runtime range alone means technical admission, not D, R or V. An omitted pair is not proof of incompatibility.

The initial V record applies to an earlier candidate with working version `0.1.10`, not to `0.2.0`. It identifies SHA-256 `aac4843d079634e47b1d6e5a6f3c3bc4f7a29d41ec35c81993ab03bef6bb798e`, Node.js `24.21.0`, CLI 99/99, full browser 599/599 and smoke 11/11 on 2026-10-19. Raw reports are retained in maintainer verification records outside the npm archive. This history and later documentation postdate that archive; this record does not certify a revised final package.

Historical plugin rows are archived evidence, not continuously maintained per-version matrices. Preserve the eleven declarations in `0.2.0`, seven in `0.3.1` and eight in published `0.3.2`. Published `0.3.3` separately declares nine targets and `0.3.4` declares nine; the six retired hosts still have last supported plugin `0.2.0`. Maintenance dates do not automatically change technical admission or history.

## Choosing an installation

Published `0.3.5` retains ten historical declarations, including the three Alphas and `0.2.2-rc.1`, without `0.2.2-rc.2`. Source candidate `0.3.6` adds `0.2.2-rc.2` and retires maintenance of `0.2.1-alpha.3`, `0.2.1-alpha.4` and `0.2.1-alpha.5`, leaving eight hosts. Candidate declarations and stage checks do not certify the final archive. `0.3.5` is the last supporting plugin for those three Alphas. Published `0.3.4`, `0.3.3` and `0.3.2` retain nine/nine/eight historical targets. The checked original `0.2.0` archive SHA-256 is `7b4156a75398daef079435af85ff1387a26e94055e17871000e945299fc66efc`; it remains the last supporting plugin for six technical retirements. `0.2.1-rc.3`, `0.2.1-rc.4` and `0.2.1-rc.5` do not inherit its declaration.

The migration target is DSH `0.2.2-rc.2` with plugin `0.3.6`, using a verified archive before publication and npm only after successful publication; the host remains an upstream RC prerelease. Published `0.3.5` remains available with its ten historical declarations. Follow the [deployment guide](deployment.md): stop, back up the complete profile/authentication state/DSH data/configuration, rehearse in an independent profile, and keep the entry private with native webserver independently disabled. Roll back to the original exact host, plugin and corresponding data backup; arbitrary new data is not promised to work on an old host. Git-only `0.1.4`, unknown pairs and undeclared future hosts receive no current support recommendation; identity/API checks remain.

DSH `0.2.2-alpha.2` is retired in `0.3.4` under the [2026-11-05 upstream failure exception](support-policy.md#upstream-failure-exception). Its native settings callback fails with newly resolved SDKs even without this plugin. Published `0.3.3` remains obtainable (archive integrity rechecked 2026-11-05), but its historical declaration does not make that fresh dependency combination usable. The migration host recommended on 2026-11-05 was `0.2.2-alpha.3`; use the current RC recommendation above for a new migration. Neither an old plugin install nor an old passing report is a repair. Historical declarations and the original SDK evidence below remain unchanged.

## Maintaining this history

These tables are maintained manually in both languages and both directions. Recheck registry metadata and tarball availability, inspect exact tag/package evidence, distinguish D/R/R\*/V, and record the check date. Update both cells when adding evidence; keep the stable anchors. A newly released plugin needs its own row and exact archive evidence. Actual DSH retirement updates current declarations, runtime adaptations, tests and this history together under the support policy; eligibility dates alone never change these tables. No inventory/history generator or dedicated CI gate is used.
