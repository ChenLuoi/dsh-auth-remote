## Scope and review rules

Plugin `0.1.9` declares support for DSH `0.1.7-rc.1`, `0.1.7-rc.2`, `0.2.0-rc.1`, `0.2.0-rc.2`, `0.2.1-alpha.1`, `0.2.1-alpha.2` and `0.2.1-alpha.3`. Development and tests default to `0.2.1-alpha.3`. Runtime admission uses `>=0.1.7-rc.1`, including prereleases; admission is not verification and still requires package identity and API checks. Versions absent from these matrices do not inherit their verification claims or automatic manual-account activation.

- Review both matrices and every affected entry before changing peers, `dsh.compatibility`, runtime admission, test targets, CI or user compatibility claims.
- `dsh-runtime`: retain an adaptation while its applicable versions intersect the supported set. When the intersection becomes empty, remove exclusive implementation and tests and update both languages, matrices, entries and guides in the same change. Keep shared security checks.
- `plugin-contract`: retire under the plugin's configuration migration policy, independently of DSH support. Plugin `0.1.9` still accepts the `allowedOrigins` input introduced by plugin `0.1.5`.
- Missing exact-version evidence requires preserving implementation and recording the gap. Passing the same test on different releases does not prove identical implementation.
- Support-range or shared host adaptation changes require CLI, browser and installation smoke coverage of the same final artifact across all declared versions. Full `DSH-ACCOUNT-001` feature regression targets only `0.2.1-alpha.3`; `0.1.7-rc.1`, `0.1.7-rc.2`, `0.2.0-rc.1`, `0.2.0-rc.2`, `0.2.1-alpha.1` and `0.2.1-alpha.2` need startup, Settings and disabled-adapter checks for that feature change. The complete CI version matrix stays unchanged.

## Capability migration and retirement workflow

1. When adding or removing DSH support, update both matrices in both languages with complete version numbers, entry IDs and evidence status.
2. When a capability changes, use the feature matrix to identify every affected release, then inspect its entries, installed package APIs, implementation and tests. Releases with the same usable API and exact-version verification may move to a shared implementation. Preserve a branch wherever capability or evidence is missing; release order is not migration evidence.
3. Record the decision per entry: exact versions retained, exact versions migrated, exclusive code/tests removed and remaining evidence gaps. Do not remove the whole entry while its applicable and supported sets intersect.
4. Public OAuth callbacks depend on both DeepSeek Platform and DSH. Platform acceptance of a public `redirect_uri` still requires verification of DSH origin policy, callback handling and UI. Retire the adaptation only under `DSH-ACCOUNT-001` conditions.
5. Review both tables and their entries manually. Do not introduce an inventory-specific generator or CI gate; continue using the existing bilingual-link and packaging checks.

## Shared security boundaries

Package identity, API checks after forward admission, concrete binding, original Host/Origin/Fetch Metadata, loopback admission, passwords/TOTP, sessions, stream revocation, storage failure and CLI confirmation apply to all declared releases. HTTPS → HTTP reverse proxy support, Host settings capability `ownsHost` and server-side native browser authentication exchange must not be removed merely because an adaptation retires.

The production entry validates the bound port after official listener initialization; failure must release the listener, admin socket and storage lock.
